# The 1.21.1 port

What differs between `main` (26.1.2) and this branch, and why. Written while doing
the port, so it is the actual list rather than a remembered one.

Read this before cherry-picking anything from `main`. Most conflicts you will hit
are on this page, and the fix is usually one line down the table.

## Stack

| | `main` | `mc-1.21.1` |
|---|---|---|

| NeoForge | 26.1.2.76 | 21.1.230 |

## API changes that need thought

**`ServerLevel` spawn queries.** 26.1 exposes both halves on `ServerLevel`; 1.21.1
splits them and hides one:

| Rule | 26.1 | 1.21.1 |
|---|---|---|
| `CHUNK_ENTITY_TICKING` | `level.canSpawnEntitiesInChunk(chunkPos)` | `level.isNaturalSpawningAllowed(chunkPos)` |
| `PLAYER_IN_SPAWN_RANGE` | `level.anyPlayerCloseEnoughForSpawning(pos)` | `level.getChunkSource().chunkMap.anyPlayerCloseEnoughForSpawning(chunkPos)`, **needs an AT** |

**`WORLD_SPAWN_DISTANCE` reads a different thing.** 26.1 has
`LevelData.RespawnData` carrying a dimension, so the check compares dimensions.
1.21.1's `isRightDistanceToPlayerAndSpawnPoint` calls `level.getSharedSpawnPos()`
on the level itself, so each level carries its own and no dimension comparison
exists. Both report the same rule honestly; the measurement behind it differs.

**Biome spawn lists.** 26.1 wraps entries in `Weighted<T>` with `.value()` and
`.weight()`. Here `MobSpawnSettings.SpawnerData` **is** the weighted entry
(`extends WeightedEntry.IntrusiveBase`): the list is a `WeightedRandomList`, the
type is the public field `entry.type`, and the weight is
`entry.getWeight().asInt()`.

**GameRules.** 26.1 reads and writes through the container
(`rules.get(KEY)` / `rules.set(KEY, v, server)`). Here it is `getBoolean(KEY)` and
`getRule(KEY).set(v, server)`.

**Registry lookups.** `HolderLookup#get(ResourceKey)` returns
`Optional<Holder.Reference<T>>` here, not a nullable value. `EntityType#create`
takes no spawn reason.

**`Item#use`** returns `InteractionResultHolder<ItemStack>`, not `InteractionResult`.
**`Item#appendHoverText`** takes a `List<Component>` rather than a
`Consumer<Component>` plus `TooltipDisplay`. The body is adapted with one
`Consumer<Component> lines = tooltip::add;` so the rest matches `main` verbatim and
cherry-picks cleanly.

**`HoverEvent`** is a class with an action enum here, not a sealed record:
`new HoverEvent(HoverEvent.Action.SHOW_TEXT, component)`.

**`CompoundTag`** has no `getStringOr` / `getIntOr`; the plain getters already
return defaults.

**Commands.** `Commands.hasPermission(level)` does not exist; the predicate reads it
off the source: `source -> source.hasPermission(Commands.LEVEL_GAMEMASTERS)`.

## The GUI is a different pipeline

26.1 renders in two phases: a screen contributes to a `GuiGraphicsExtractor` in
`extractRenderState`. 1.21.1 has the single-phase `render(GuiGraphics, mouseX,
mouseY, partialTick)`.

This was smaller than it sounds, because the screen only ever calls four drawing
methods and three are identical. `gui.text(font, ...)` becomes
`gui.drawString(font, ...)`; `fill`, `enableScissor`, and `disableScissor` are the
same. The ordering rule survives intact: our panel first, `super.render` last, or
the search box ends up buried under the panel background.

`mouseClicked(MouseButtonEvent, boolean)` becomes
`mouseClicked(double, double, int)`.

## GameTests are registered differently

`main` registers a body into `Registries.TEST_FUNCTION` plus a `TestData`. Here it
is the annotation form: `@GameTestHolder` and `@PrefixGameTestTemplate(false)` on
the class, `@GameTest(templateNamespace = ..., template = "empty_5x5x5",
timeoutTicks = N)` on a `public static void name(GameTestHelper)`.

**The test bodies are deliberately identical between branches.** Only the
declaration line and the registrar differ, so a fix plus its regression test
cherry-picks with a small conflict on the signature rather than a rewrite.

Two consequences:

- Test ids carry the declaring class here:
  `spawndetective:worldruletests.gamerule_off_blocks_everything` instead of
  `spawndetective:gamerule_off_blocks_everything`. `/test run spawndetective:*`
  works on both.
- `GameTestAssertException` takes a plain `String` here, not a `Component` and a
  tick.

## Resources

- **`neoforge.mods.toml` needs `loaderVersion`.** Leaving it out does not warn: FML
  rejects the mod with "is not a valid mod file", which first shows up as the JUnit
  JVM refusing to start. That error message names the classes directory, not the
  missing field, so it reads like a build problem.
- **`pack.mcmeta` uses a single `pack_format` (48).** The `min_format`/`max_format`
  pair is later.
- **Recipe ingredients are objects**: `{"tag": "minecraft:saplings"}` and
  `{"item": "minecraft:stick"}`, not the flat `"#minecraft:saplings"` string form.
  The **result still uses `id`**, same as `main`. Getting this wrong is silent: the
  datapack drops the recipe and the item is simply uncraftable, so
  `RecipeIntegrityTest` asserts the shape this version actually loads.
- `data/<ns>/structure/` and `data/<ns>/recipe/` are singular on both versions.
- There is no `assets/<ns>/items/` model-definition layer here; `models/item/` is
  the whole story.

## Access transformers

The two branches need **different** entries, so this file will always conflict on a
cherry-pick. Resolve it by keeping this branch's version.

- `ChunkMap.anyPlayerCloseEnoughForSpawning` - needed here, not on `main`.
- `NaturalSpawner$SpawnState.spawnPotential` and `.localMobCapCalculator` - needed
  on **both**.

A trap worth naming: moddev applies your AT to the artifact it decompiles, so once
an entry exists, the extracted sources show that member as public. Reading the
decompiled source to decide whether you need an AT will tell you that you do not.
The compiler is the honest check.

## Development gotcha: `run/` is not branch-aware

`run/mods` is gitignored and shared across branches, so the Jade jar dropped in for
a 26.1 session is still there after `git switch mc-1.21.1`, and the game refuses to
start:

```
Mod jade requires neoforge 26.1-beta or above
Currently, neoforge is 21.1.230
```

Clear or park `run/mods` when switching lines. `scripts/fetch_dev_mods.py` fetches
the version this branch wants.

## What is NOT different

The engine. `SpawnAuditor`'s logic, the rule set, the ordering, the attribution
technique, `SpawnVerdict`, the reports, and the payloads are the same code. That is
the point: both lines answer the same question the same way, and
`docs/spawn_pipeline_map.md` stays one contract rather than two.
